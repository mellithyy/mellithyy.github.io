NetAct XML Loader

The day’s network dumps in the engineers’ database in 20 minutes, not 6 hours

The problem

Loading the day’s network configuration dumps into the engineers’ database took about six hours.

What I built

A Python tool that reads the XML dumps once, fills the same database tables and compares every cell with the old import.

The result

About 20 minutes instead of about six hours, used by the team every day.

What it is

At Nokia, October 2024 to April 2025: a Python tool that reads a mobile network’s daily configuration dumps, every setting of every 2G, 3G, 4G and 5G network element, and fills the database the engineers query in about 20 minutes.

The question

Every day the network’s management system, NetAct, exports the whole configuration of the network as XML: every managed object and every parameter. The engineers do not read that XML. They query an Access database built from it by the import step of NetAct Plan Editor.

That import took about six hours for the day’s dumps, and nobody could use the database until it finished. The question: could the same database, with the same tables, keys and values, be built straight from the XML in a fraction of the time, and could we prove that it matches?

What it does

One-command load

Give it a dump file and it reads the technology and the date from the name, copies the matching Plan Editor template and fills it. The template’s own metadata tables decide every table, every key and every type, so one tool serves over 1,000 table types from 2G to 5G.

Every technology in about 20 minutes

On one day’s dumps the four runs took about 21 minutes together: 2G, 3G and 4G, then the full dump that holds them all. The 4G file alone is about 4.8 GB. The old import took about six hours.

A report that checks every cell

A second tool opens Plan Editor’s database and this one side by side, turns every table into rows of key, parameter and value, and lists every cell that differs: a Changes sheet with each difference and a Summary sheet that counts them by table and state.

How it works

  1. 01Stream the dump The XML is read one managed object at a time. Each object becomes a row of its class and is then cleared from the parser, so a 4.8 GB file is never held as one tree.
  2. 02Let the template decide The template’s metadata tables say which class fills which table, which XML names become which columns, and which tables are filled from another class. No table has code of its own.
  3. 03Split each name into keys Every object’s name is a path, such as BSC-412/BCF-17/BTS-3. A pattern built from the template’s name format splits it into key columns; a name that breaks its format is listed, not loaded.
  4. 04Keep every space, set every type Plan Editor keeps a space at the end of a name; Access would trim it. Such names are marked before the load and restored after it. Column types and widths come from the parameter declarations.
  5. 05Load in bulk Each table is written as a CSV file with its own schema file and loaded with one Jet SQL statement through Access, never row by row.
  6. 06Compare cell by cell Both databases are turned into rows of key, parameter and value and joined. Every difference goes to the Changes sheet with its state; the Summary sheet counts them.
Read from the template, not written in code
  • Which class fills which table
  • Parameter names, types and widths
  • Name formats and key columns

How I checked it

Every version was run end to end on real dumps: one command took a day’s dump archive with Plan Editor’s database, ran the tool and the comparison, and returned the report. Open cases stayed in a test-case log until each one was fixed or explained.

  • Names that end with a space are kept exactly as Plan Editor keeps them.
  • Names that break their own format, such as a four-digit value where the rule asks for five, are listed for the team.
  • Where a difference was Plan Editor’s fault, not the tool’s, it was written down with the evidence.

What I would do differently

I would keep every version in Git from the first day instead of copying files, and write each class’s rows to disk while the dump streams, so memory stays flat on the largest files.
